> 更新：2026-10-24
> 关联实现：`src/baseline-rag-memory.ts`
> 实验入口：`tests/ab_branch_isolation.ts --arms=isolated,shared,rag`

---

## 一、为什么补这一档

原来的 `isolated` 与 `shared` 都是项目内部构造的注入条件：

- `isolated`：状态表和知识图谱按 `branchId` 过滤；
- `shared`：把两套互斥事实直接注入同一份内部记忆。

这能证明“分支隔离机制有用”，但还不是对既有检索式记忆系统的外部对比。
审稿人可以直接指出：`shared` 是作者自己定义的强泄漏条件，不是外部方法。

因此新增 `rag` 档：

1. 打开同一分叉点后，把分支 A、分支 B 的事实都写入一个**单线共享检索池**；
2. 每轮用分叉点与当前尾段构造 query，检索 top-3；
3. 检索结果作为外部记忆注入 Prompt；
4. 当前分支新生成的段落继续写回同一检索池；
5. 不启用项目内置状态表和知识图谱。

这模拟了“只有一个检索库、没有 branchId 维度”的常见 RAG 记忆系统。

## 二、实现口径

### 2.1 检索方式

当前环境是 DeepSeek 文本 API，未配置 embedding 端点，因此正式可运行版本使用：

- 中文连续文本切成字符二元组；
- BM25 计算 query 与文档的相关度；
- 返回 top-k 原文片段。

如果配置以下变量，会改为向量检索：

```text
AI_EMBEDDING_BASE_URL=...
AI_EMBEDDING_API_KEY=...
AI_EMBEDDING_MODEL=text-embedding-3-small
```

论文里必须如实写检索方式。当前没有 `AI_EMBEDDING_MODEL` 时应写“BM25 检索式记忆”，
不能写成 embedding RAG。

### 2.2 三档的关系

| 档位 | 记忆空间 | 分支过滤 | 注入方式 |
|---|---|:---:|---|
| `isolated`（本文） | 分支 A、B 分库存放 | 有 | 状态表 + 图谱 |
| `shared`（内部强泄漏对照） | 两套事实都挂到 A | 无 | 结构化事实直接注入 |
| `rag`（外部检索基线） | 两套事实同一检索池 | 无 | 按上下文检索 top-k |

`shared` 与 `rag` 都不是本文方法，但回答的问题不同：

- `shared`：如果完全不区分分支，直接把所有记忆塞给模型，会怎样；
- `rag`：如果采用常见的单线检索记忆，只把相关片段塞给模型，会怎样。

### 2.3 指标

保持与主实验一致，不另换一套对自己有利的指标：

- 分支 B marker 关键词命中率；
- LLM-as-Judge 跨分支污染率（主指标）；
- 两法逐段一致率；
- 逐故事配对差值；
- 配对 t 检验与 Bonferroni 校正。

`rag` 与 `isolated` 的差值定义为：

```text
RAG 相对分支隔离的泄漏增量 = RAG 污染率 − isolated 污染率
```

## 四、样本量判断：不扩故事，先补外部基线

当前不建议继续把故事数从 20 往上加，原因是现有证据已经足够稳定：

- 20 组逐故事 **19 胜、1 平、0 负**；
- 配对 `t = 8.88, df = 19, p = 3.4e-8`；
- 最保守的 Bonferroni `k=4` 临界值 2.759，实际 t 仍高出一大截；
- 均值差 0.550，SE 0.062，95% 置信区间约为 **[0.420, 0.680]**。

继续扩样的边际价值很低。更大的风险是**没有外部方法对比**，而不是样本数不够。

实验 A 也一样：30 个故事是按功效分析预先确定的，`state` 与 `both` 显著，
`graph` 不显著；继续加故事不会自动改变“图谱单独无效”的结论。

因此下一阶段的正确顺序是：

1. 先在相同 20 组故事上补 `rag` 外部基线；
2. 三档必须在同一轮代码、同一模型、同一判定协议下重跑，才能做逐故事配对；
3. 若 `rag` 结果稳定，再决定是否需要扩大样本，而不是现在先加故事。

## 五、建议跑批顺序

### 5.1 小样本 smoke

```bash
npx tsx tests/ab_branch_isolation.ts \
  --stories=2 --segments=2 --rounds=1 \
  --arms=isolated,shared,rag \
  --tag=ragsmoke
```

检查：

- 每个 `rag` 记录都应看到“BM25 / embedding”提示；
- `rag` 的 prompt 中确实出现“单线 RAG 检索记忆”；
- 隔离档不应因为 RAG 初始化而漏进乙分支角色；
- 三个档位都能落盘并生成 judge 结果。

### 5.2 正式三档跑批

```bash
npx tsx tests/ab_branch_isolation.ts \
  --stories=20 --segments=5 --rounds=3 \
  --arms=isolated,shared,rag \
  --tag=rag20
```

预计：

- 20 × 3 × 5 × 3 = **900 次续写**；
- 再加 900 次 Judge；
- 在 AIRequestQueue 20 次/分钟的限制下，至少需要数小时。

这一批应作为独立进程运行，不能挂在会退出的会话上。

## 六、论文写法

建议在实验 B 中并列报告三行：

| 方法 | 记忆组织 | 是否使用分支信息 |
|---|---|:---:|
| 分支隔离（本文） | 状态表 + 图谱，按 branchId 过滤 | 是 |
| 单线结构化记忆 | 两分支事实直接合并 | 否 |
| BM25/Embedding RAG | 单线检索池，top-k 注入 | 否 |

主结论仍然只使用 `judgeContaminationRate`，关键词法作为佐证。
如果 RAG 的泄漏率与 `shared` 同量级，说明问题不是某一种注入格式造成的，而是
“单线记忆缺少分支维度”这一结构性缺陷；这比只与内部 `shared` 对比更有说服力。
